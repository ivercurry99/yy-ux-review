# 方法论：评分、定级、权衡与验证闭环

## 一、维度评分规则（1-5 分）

对任务流经过的每个环节，逐维度打分；最后取各环节平均分作为该维度总评。

| 分数 | 含义 | 判定依据 |
|---|---|---|
| 5 | 优秀 | 无明显问题，可作为同类参考 |
| 4 | 良好 | 有小瑕疵，不影响任务完成 |
| 3 | 及格 | 有明确问题，造成可感知的卡顿或困惑 |
| 2 | 较差 | 问题导致部分用户走偏、重试或求助 |
| 1 | 失效 | 问题阻断任务，或导致用户放弃/流失 |

**打分纪律**：
- 每个分数必须有证据（截图/路径/计时）支撑；证据不足打"存疑"，不写分数，报告中说明验证方式。
- 维度对当前任务流**不适用**时标 N/A（如纯阅读产品无"容错"场景），并说明理由。禁止凑分。
- 不允许"整体印象分"——分数必须逐环节产生再聚合。

## 二、问题严重度分级

| 级别 | 定义 | 示例 |
|---|---|---|
| 🔴 致命 | 阻断核心任务，或造成数据/资金损失、信任崩塌 | 提交支付失败且已填信息清空；结算隐藏费用 |
| 🟠 严重 | 显著增加完成难度，导致大量用户走偏或放弃 | 关键功能入口违反心智模型，首步点击即走偏 |
| 🟡 次要 | 造成卡顿、困惑或情绪损耗，但用户能自行恢复 | 报错文案不说明格式；术语前后不一 |
| 🔵 建议 | 优化机会，当前不构成障碍 | 可增加批量操作；空态文案可更有人味 |

**排序公式**：优先级 = 严重度 × 对核心任务的影响范围（影响环节数 × 涉及用户比例估计）。

## 三、维度权衡裁决原则

维度间冲突时，按以下顺序裁决：

1. **底线维度不可交易**：可达（无障碍）、可信赖（透明）是底线，不为效率或愉悦牺牲。
2. **回到锁定的用户与场景**：阶段 1 锁定的目标用户是谁，就为谁优化。新手产品是新手视角，效率工具是老手视角。
3. **后果分级干预**：容错防护强度 = 后果严重性 × 恢复成本。低风险操作不弹窗，高风险操作必须确认。
4. **取舍必须写明**：报告中每个权衡决策要标注"牺牲了什么、换来什么、依据是什么"。

## 四、验证闭环指标（优化后必采）

每个修复建议必须绑定至少一个可验证指标，优化前后对比：

| 指标 | 定义 | 采集方式 |
|---|---|---|
| **任务完成率** | 独立完成目标任务的用户比例 | 可用性测试 / 埋点漏斗 |
| **平均耗时** | 从任务起点到完成的时间 | 埋点时间戳 / 测试计时 |
| **错误率** | 任务过程中出错（误点、走错、重试）的比例 | 埋点 / 测试观察记录 |
| **用户反馈** | NPS 分数 + 开放式反馈关键词 | 问卷 / 访谈 |

**执行闭环**：

```text
选定用户角色 + 核心任务
  → 沿流程逐项检查 10 维度（记录位置/阻碍/影响层级）
  → 按严重度排序修复
  → 上线后采集四维指标
  → 与基线对比，验证每一次优化有据可依
```

**纪律**：没有基线数据时，先建立基线再优化；禁止"优化完即宣告成功"。

```text
目标用户：【谁，新手/老手，数字素养】

产品类型：【工具 / 内容 / 交易 / 社交 / 其他】
输入材料：【URL / 截图 N 张 / 录屏 / PRD / 设计稿】
假设清单：【用户未提供信息时，列出所有自行假设的条目】
```
